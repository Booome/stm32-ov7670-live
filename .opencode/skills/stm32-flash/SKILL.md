# STM32 st-flash Flashing

## Overview

Flash a freshly compiled `.bin` to the STM32F103C8T6 via the ST-Link probe
using `st-flash`, then `--reset` to run it. This is the fast path after a
CMake build when you want the firmware running on the board.

## When to Use

- After `cmake --build` you need to burn the new firmware onto the board.
- `st-flash` reports it cannot find / connect to the device.
- You want a one-liner flash + reset instead of driving openocd.

**When NOT to use:** byte-complete boot capture needs openocd
`reset halt` / `reset run` — use the serial-capture skill instead
(`.opencode/skills/serial-capture/`).

## Quick Reference

```bash
# 1. Make sure no openocd is holding the ST-Link probe
pkill openocd          # ignore "no process found"

# 2. Flash + reset (run from repo root, or use an absolute path)
st-flash --reset write build/Debug/stm32-ov7670-live.bin 0x08000000
```

## Details

- Binary path: `build/Debug/stm32-ov7670-live.bin` — rebuild before
  flashing, never reuse a stale `.bin`.
- **The `.bin` is NOT generated by CMake.** `cmake --build` only emits the
  `.elf`; the `.bin` is produced by a manual objcopy. If you flash without
  regenerating it you burn a stale binary:
  ```bash
  arm-none-eabi-objcopy -O binary \
    build/Debug/stm32-ov7670-live.elf build/Debug/stm32-ov7670-live.bin
  ```
  Always objcopy fresh, and sanity-check the `.bin` size/timestamp changed
  before programming.
- `--reset` releases reset and runs the firmware after programming.
- The board uses the ST-Link V2 probe, which is shared with openocd — never
  run `st-flash` and `openocd` concurrently.

## Common Mistakes

- **openocd still running** → `st-flash` fails to connect to the probe.
  Kill it first: `pkill openocd`, then retry.
- **Wrong cwd / stale binary** → you flash an old build; objcopy a fresh
  `.bin` from the latest `.elf` (see Details) and confirm its size/timestamp
  changed before programming. A symptom of flashing a stale build is the
  firmware stopping early / missing recently added output.
- **`st-flash reset` loses early boot output** → `st-flash reset` has no
  hold/release mode (arguments are silently ignored), so the first serial
  lines after boot may be gone. When the very first bytes matter, use the
  serial-capture skill instead.
